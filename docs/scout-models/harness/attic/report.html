Looking for a small CPU model to organize tasks, summarize tickets, and write throwaway Python. The two fastest models fabricate assignees. The one to run is a 3B that nobody would call exciting.

Intel i7-8700 · 6 cores · AVX2, no VNNI ~19–21 GB/s effective llama.cpp a3b1eff Q4 GGUF · 6 threads pinned
Run this

granite-4.1-3b

Perfect on both suites — 23/23 tasks, 24/24 on the traps. 11.1 t/s decode, and among the least verbose tested: 217 tokens to answer three hard probes. Apache 2.0, 1.95 GiB.

If you want speed

LFM2-2.6B

13.7 t/s and still perfect on structured extraction. Slightly blunter on summary attribution. Use LFM2 — not LFM2.5, which can't be stopped from thinking.

Don't

Qwen3-1.7B · Qwen3.5-2B

The fastest things here, and they pass casual tests. Both invented a task owner on realistic standup notes. A fabricated assignee in a tracker costs more than a slow answer.

Speed

Decode is bandwidth-bound, so the file size mostly predicts the rate — but the box streams at ~19–21 GB/s in practice, not the 31.8 GB/s a raw memory benchmark suggests. Every estimate built on "32 ÷ file size" came in about 35% hot.

The load-bearing result is the rule at the bottom of the table: the entire 4B class decodes no faster than the 35B-A3B already running on this host. Anything at or below that line is paying capability for nothing.

One trap worth naming: Qwen3.5-4B at Q3_K_M is slower than Qwen3-4B at Q4_K_M despite the smaller file. Q3 unpacking costs compute, and an AVX2-only core has none to spare. Don't reach for Q3 quants on this host.

The flag that matters more than throughput

The first quality run nearly wrote off Qwen3.5-2B. Asked to pull four action items out of a short message, it spent its entire 1400-token budget inside a <think> block — visibly second-guessing itself, "Wait, check the JSON keys…" — and emitted no answer at all.

Same model, same prompt, one parameter:

Thinking on (default)

96.7s

1400 tokens burned. No answer produced.

enable_thinking: false

9.3s

109 tokens. Correct answer.

What to take from it

Judge these models by tokens emitted per answer, not benchmark t/s. A 20 t/s model that deliberates for 800 tokens loses badly to a 13 t/s model that answers in 80.

This also disqualified one candidate outright. LFM2.5-2.6B ignores the flag — its chat template always thinks — so it took 266 seconds across three tasks and returned nothing for the summary. The older, non-thinking LFM2-2.6B is unaffected and is the speed pick above.

Where the fast models break

The first faithfulness test was too easy: no model invented a certificate expiry, a firewall, or a DNS cause, and six tied at the top of the task suite. A test everyone passes ranks nothing, so I wrote a harder one — an unowned blocked task, an owner attached to a different task, an item with no date, and a line that looks like a task but isn't.

Standup notes given to every model: "The invoice export is still broken — we can't start on it until legal signs off on the data retention question. Emily said she'd take the migration script once the export is fixed. We should also bump the Postgres version at some point. Kevin is out until the 14th."

Also worth knowing

  • Binary / BitNet Kernels are fine; quality isn't. bitnet.cpp's AVX2 paths are genuine — its flagship benchmark CPU is itself AVX2-only — so the earlier Ternary-Bonsai failure was that PrismML fork's scalar fallback, not an ecosystem limit. But BitNet-2B-4T scores IFEval 53.5, far below every dense model here. Not worth revisiting until someone ships ternary with modern post-training.
  • Long tickets granite-4.0-h-micro is hybrid Mamba2 with constant KV memory, so its rate should hold as threads grow while the dense models sag. It ties granite-4.1-3b on quality and trails it at short context. Benchmark both at depth 4k/16k before committing if ticket threads run long.
  • Grader honesty My first grader docked every model for not saying "cause unknown" on the summary test. Re-reading the outputs, they were right and the check was wrong — they reported the observed TLS timeout without asserting a root cause. Fixed before scoring. The "doesn't attribute claims" flag still on the Granites is likewise a regex artifact; granite-4.1's summary attributes properly and preserves "root cause has not yet been identified."
  • Honest margin Yes, there's something faster than what's running — but it's 1.2–1.7× decode, not the 3–5× the file-size math implies. The real win isn't t/s: a 2 GB model answers a ticket in 10–25s instead of 60s and leaves the box free for inferq.

Running it

# validated config — keep it off inferq's cores
taskset -c 0-5 /models/llamacpp-main/build/bin/llama-server \
  -m /models/small-models/granite-4.1-3b-Q4_K_M.gguf \
  -t 6 -c 8192 --jinja --host 127.0.0.1 --port 8099

# the client MUST send both of these
"chat_template_kwargs": {"enable_thinking": false},
"max_tokens": 512   # so a runaway think loop times out instead of hanging
Greedy decoding (temperature 0), so these numbers reproduce on the same build.
